# Техническое задание для ИИ: образовательная игра-редактор «Меткий ответ»

> Этот документ является исчерпывающей инструкцией для ИИ-разработчика. Не ограничивайся прототипом или статичным макетом: создай полностью работающий редактор, игровую механику, сохранение проектов и автономный экспорт игры.

## 1. Роль ИИ и ожидаемый результат

Ты одновременно выступаешь как senior frontend-разработчик, инженер игровой логики, UX/UI-дизайнер, специалист по доступности и педагогический гейм-дизайнер.

Требуется разработать браузерное приложение — современный конструктор учебных игр в духе классической механики охоты на летящие цели. Учитель настраивает игру в левой панели, постоянно видит и тестирует результат в правом окне предпросмотра, сохраняет проект и экспортирует автономную HTML-игру для учеников или код для вставки в Genially.

Финальный результат должен быть готовым приложением, а не набором демонстрационных экранов. Все кнопки, формы, игровые состояния, импорт и экспорт обязаны работать.

## 2. Главные принципы

1. **Учитель не должен программировать.** Все настройки выполняются через понятные поля, переключатели, карточки, выбор цвета, загрузку файлов и drag-and-drop.
2. **Предпросмотр всегда живой и стабильный.** Изменения отражаются сразу, но игровая сцена не перезагружается, не мигает, не теряет фокус и не сбрасывает текущий тест без необходимости.
3. **Экспорт автономен.** Скачанный HTML запускается двойным щелчком в современном браузере без сервера, сборщика и интернета.
4. **Редактор пригоден для урока.** Крупные элементы, ясные подписи, предотвращение случайной потери данных, доступность с клавиатуры и корректная работа на ноутбуке/интерактивной панели.
5. **Визуальная стилистика авторская.** Можно вдохновляться композицией референсов, но нельзя копировать название, логотип, музыку, персонажей или пиксельные спрайты оригинальной Duck Hunt.

## 3. Референсы из корня проекта

Обязательно изучи перед реализацией:

- `1.png` (1920×1080) — современная яркая сцена 16:9: небо, облака, деревья, несколько слоёв травы, крупный прицел, цель в центре, пауза сверху справа, раунд/патроны/индикатор целей/счёт снизу.
- `2.jpg` (1280×720) — ретро-композиция начала раунда: помощник выбегает в нижней части сцены, номер раунда расположен сверху.
- `3.jpg` (780×439) — помощник появляется из высокой травы и демонстрирует пойманную цель.

Перенести из референсов:

- читаемую сцену 16:9;
- многослойный фон и траву переднего плана, из которой появляются персонажи;
- ясные HUD-индикаторы: раунд, очки, серия/прогресс и оставшиеся выстрелы;
- крупный контрастный прицел, следующий за указателем;
- короткие сценки с помощником в начале/конце раунда;
- яркую аркадную обратную связь.

Не переносить буквально:

- оригинальные спрайты уток и собаки;
- оригинальные звуки, шрифты, логотипы и точную пиксельную графику;
- насмешливую реакцию помощника на ошибку: для учебной среды реакция должна быть поддерживающей и доброжелательной.

## 4. Рекомендуемый технологический стек

Если в проекте уже есть стек, следуй ему и не переписывай приложение без причины. Если проект пустой, используй:

- React + TypeScript + Vite;
- CSS Modules либо обычный CSS с дизайн-токенами; не привязывай экспорт к внешнему UI-фреймворку;
- Zustand или аккуратно организованный React Context/useReducer для состояния;
- Zod для проверки импортируемого JSON;
- canvas или DOM/CSS transforms для игровой сцены; предпочтение DOM/CSS, если он обеспечивает стабильные 60 FPS и доступность;
- Web Audio API для простых авторских звуков либо встроенные data URI;
- IndexedDB для автосохранения крупных пользовательских ассетов, localStorage — только для небольших настроек;
- Vitest + Testing Library для логики редактора, Playwright для ключевых сквозных сценариев.

Не допускай обязательных CDN-зависимостей в экспортированном файле. Если основное приложение использует библиотеки, экспорт должен собирать автономный runtime с инлайновыми CSS, JS и ассетами.

## 5. Общая компоновка редактора

### 5.1. Верхняя панель

Разместить:

- название приложения «Меткий ответ» (рабочее название можно вынести в конфигурацию);
- редактируемое название проекта;
- индикатор состояния «Сохранено» / «Есть несохранённые изменения» / «Автосохранение…»;
- Undo и Redo;
- кнопки «Загрузить проект», «Скачать проект», «Скачать HTML игры», «Скопировать код для Genially»;
- кнопку «Справка»;
- управление масштабом интерфейса при необходимости.

Опасные или необратимые действия подтверждать. Перед закрытием вкладки предупреждать только при наличии несохранённых изменений.

### 5.2. Основная область

На широких экранах:

- слева — панель инструментов шириной примерно 380–460 px;
- справа — гибкая область предпросмотра;
- между ними — перетаскиваемый разделитель;
- панель настроек прокручивается независимо от предпросмотра;
- предпросмотр остаётся видимым при прокрутке длинной формы.

На узких экранах:

- переключатель вкладок «Настройки» / «Предпросмотр»;
- редактор не обязан быть удобным на телефоне, но не должен ломаться;
- экспортированная игра обязана корректно масштабироваться на телефонах и планшетах.

### 5.3. Левая панель инструментов

Организовать как аккордеон или вертикальные вкладки:

1. «Основное»;
2. «Язык и тексты»;
3. «Сцена»;
4. «Цели»;
5. «Помощник»;
6. «Задания»;
7. «Оформление задания»;
8. «Правила и баллы»;
9. «Звук»;
10. «Экспорт».

Активная секция и выбранный объект должны быть очевидны. Для сложных параметров показывать короткую подсказку.

### 5.4. Правая область предпросмотра

- рамка устройства с фиксированным игровым соотношением 16:9;
- варианты масштаба «Вписать», 50%, 75%, 100%;
- кнопки «Начать тест», «Перезапустить», «Пауза», «Развернуть»;
- переключатель безопасной зоны интерфейса;
- статус режима: «Редактирование» или «Тест игры»;
- в режиме редактирования клики по объекту сцены выбирают соответствующий раздел настроек;
- в режиме теста работают настоящие выстрелы, задания, баллы и завершение игры.

## 6. Требование без мигания предпросмотра

Это критический критерий приёмки.

- Никогда не пересоздавай iframe/canvas/root-компонент предпросмотра при каждом вводе символа.
- Храни стабильный экземпляр игрового runtime и передавай в него точечные обновления состояния.
- Не используй изменяющийся `key` на корне предпросмотра.
- Не меняй `src`/`srcDoc` iframe при обычном редактировании.
- Текстовые и цветовые изменения применяй через состояние/CSS custom properties.
- Загруженные изображения декодируй заранее (`img.decode()`), после чего атомарно меняй ссылку; до готовности оставляй прежнее изображение.
- Для тяжёлых изменений используй debounce 100–200 мс, но поля ввода обновляй без задержки.
- Игровую сессию сбрасывай только по кнопке «Перезапустить» либо при структурном изменении, несовместимом с текущим тестом. В последнем случае покажи ненавязчивое уведомление.
- Проверить отсутствие белой вспышки и потери позиции при наборе не менее 30 символов подряд, смене цветов и размера шрифта.

## 7. Локализация

### 7.1. Встроенные языки

Минимум:

- русский;
- английский;
- испанский;
- немецкий;
- французский;
- итальянский;
- казахский.

Архитектура должна позволять добавлять новые словари без изменения компонентов.

### 7.2. Поведение выбора языка

После выбора языка автоматически и мгновенно меняются **все системные плашки в предпросмотре**:

- «Раунд», «Счёт», «Серия», «Выстрелы»;
- «Старт», «Пауза», «Продолжить», «Начать заново»;
- «Выберите один ответ», «Выберите несколько ответов», «Расставьте по порядку»;
- «Проверить», «Готово», «Следующий вопрос»;
- сообщения о верном/неверном ответе;
- итоги игры и кнопки результата.

Пользовательские вопросы и ответы не переводить автоматически: это авторский учебный контент. Рядом с выбором языка явно написать: «Системные надписи будут переведены; ваши задания останутся без изменений».

Добавить редактор системных текстов для текущего языка и кнопку «Вернуть стандартные переводы». Сохранять переопределения в проекте.

Не собирать фразы конкатенацией. Учесть множественные формы и длинные переводы. Все системные строки должны находиться в словарях, а не быть захардкожены в JSX.

## 8. Библиотека сцен и загружаемый фон

### 8.1. Встроенные авторские фоны

Предоставить минимум 8 стилистически согласованных вариантов:

1. солнечная лесная поляна;
2. осенний парк;
3. зимний лес;
4. тропические джунгли;
5. фермерское поле;
6. морское побережье;
7. космическая станция с иллюминатором;
8. сказочная библиотека/магическая академия.

Для каждого фона нужны миниатюра, полноразмерная версия 16:9, данные о безопасной зоне и подходящие цвета HUD. Желательно разделить фон на задний план, средний план и переднюю маску, чтобы цели могли «вылетать» из-за травы/кустов/объектов.

### 8.2. Пользовательский фон

- загрузка PNG, JPEG, WebP;
- drag-and-drop и обычный выбор файла;
- проверка MIME-типа и разумного лимита размера;
- предпросмотр до применения;
- режимы `cover`, `contain`, «растянуть»;
- позиционирование по X/Y и масштаб;
- настройка затемнения/размытия для читаемости UI;
- возможность удалить пользовательский фон и вернуться к встроенному;
- хранение в проекте как data URL/Blob, чтобы экспорт оставался автономным.

## 9. Цели: утки и альтернативные животные

Термин «цель» использовать в коде как универсальную сущность. В интерфейсе можно писать «Утки и другие цели».

Встроенная библиотека должна включать доброжелательные авторские персонажи, по которым ученик «попадает» мягким световым маркером, краской или фото-вспышкой, без крови и жестокости:

- классическая мультяшная утка;
- гусь-почтальон;
- сова со свитком;
- попугай-исследователь;
- пингвин в шарфе;
- летучая мышь;
- бабочка;
- пчела;
- дракончик;
- летающий робот;
- бумажный самолётик;
- волшебная книга.

Для каждого персонажа предусмотреть состояния/анимации:

- ожидание (если нужно);
- появление;
- полёт минимум в двух направлениях;
- попадание без насилия (звёздочки/вспышка/заморозка кадра);
- уход за границу;
- миниатюра в библиотеке.

Настройки целей:

- один персонаж или случайный набор;
- количество целей в раунде;
- одновременное число целей;
- скорость: медленная/средняя/быстрая и точное значение;
- размер;
- траектории: прямая, дуга, волна, зигзаг, случайная безопасная;
- время на экране;
- пауза между появлениями;
- число выстрелов;
- включение/отключение попадания по прозрачным областям спрайта (если реализована pixel-perfect hit area);
- запрет появления под HUD и за пределами безопасной зоны.

Пользователь может загрузить свой PNG/WebP/GIF с прозрачностью. Для статичного изображения создать лёгкую анимацию полёта CSS-трансформациями. Дать настройку размера, точки привязки и области попадания. SVG принимать только после безопасной очистки либо не принимать вовсе.

## 10. Помощник вместо собаки

Встроенные варианты:

- добрый пёс-следопыт;
- лиса-наставница;
- енот-лаборант;
- кот-профессор;
- медвежонок;
- робот-помощник;
- совёнок-библиотекарь;
- капибара-тренер.

Поведение помощника:

- коротко появляется перед началом раунда;
- показывает подсказку или номер раунда;
- после серии успехов поздравляет;
- после промаха поддерживает нейтральной фразой («Попробуем ещё!»), но не высмеивает ученика;
- в конце показывает результат;
- его можно полностью отключить.

Разрешить загрузить собственного помощника (PNG/WebP/GIF), настроить масштаб, положение, имя и реплики. Реплики должны поддерживать строки для всех выбранных системных языков. Пользовательский ассет включается в JSON проекта и автономный HTML.

## 11. Игровой процесс

### 11.1. Состояния игры

Реализовать конечный автомат как минимум со состояниями:

`READY → ROUND_INTRO → TARGET_FLYING → TARGET_HIT → TASK_OPEN → ANSWER_FEEDBACK → ROUND_CONTINUE → ROUND_RESULT → GAME_RESULT`, а также `PAUSED`.

Переходы должны быть явными и тестируемыми. Нельзя допускать двойного открытия вопроса, начисления баллов дважды или появления новой цели под модальным окном.

### 11.2. Управление прицелом и выстрел

- на desktop прицел следует за мышью внутри сцены;
- на touch попадание выполняется касанием;
- поддержать клавиатуру: стрелки перемещают прицел, Enter/Space выполняет выстрел;
- системный курсор внутри сцены можно скрыть только в тестовом/игровом режиме;
- прицел должен быть контрастным на любом фоне: двойная обводка или динамический контраст;
- выстрел сопровождается короткой безопасной вспышкой, звуком и лёгкой отдачей, если анимации разрешены;
- не использовать резкое полноэкранное мерцание;
- выстрел мимо уменьшает число доступных попыток, если этот режим включён;
- попадание временно блокирует повторные клики по цели.

### 11.3. Связь цели и задания

По попаданию:

1. приостановить движение остальных целей;
2. проиграть короткую анимацию попадания;
3. открыть окно задания, связанного с целью;
4. дать ученику ответить или озвучить ответ;
5. показать результат;
6. закрыть задание вручную или автоматически по настройке;
7. продолжить раунд.

Распределение заданий: последовательно, случайно без повторов либо привязка конкретного задания к конкретному типу цели. Если заданий меньше, чем целей, разрешить повтор или завершить игру — выбор учителя.

## 12. Редактор заданий

### 12.1. Список заданий

- карточки с номером, типом, началом вопроса и статусом заполнения;
- добавить, дублировать, удалить с подтверждением;
- drag-and-drop сортировка и кнопки перемещения для клавиатуры;
- фильтр по типу;
- массовое сворачивание;
- предупреждение о незаполненных данных;
- импорт/экспорт банка заданий в JSON (дополнительно к проекту).

### 12.2. Общие поля задания

- формулировка вопроса;
- необязательное пояснение/контекст;
- необязательное изображение (PNG/JPEG/WebP) с alt-текстом;
- тип задания;
- количество баллов;
- необязательное ограничение времени;
- обратная связь для верного ответа;
- обратная связь для неверного ответа;
- подсказка;
- переключатель перемешивания вариантов.

### 12.3. Тип «Один ответ»

- минимум 2 варианта;
- radio-переключатели;
- ровно один правильный ответ;
- нельзя сохранить задание без отмеченного правильного ответа;
- варианты можно добавлять, удалять и сортировать.

### 12.4. Тип «Множественный выбор»

- checkbox-переключатели;
- один или несколько правильных вариантов;
- режим оценки: только полное совпадение либо частичные баллы;
- при частичной оценке ошибочно выбранный вариант уменьшает балл, но итог задания не ниже нуля;
- кнопка «Проверить» активна после выбора хотя бы одного варианта.

### 12.5. Тип «Без ответа (устный вопрос)»

- поле ответа ученику не показывать;
- показывать вопрос и необязательную подсказку;
- кнопки «Показать ответ» (если учитель заполнил эталон) и «Готово»;
- опциональный режим самооценки: «Ответил(а)» / «Нужна помощь»;
- по умолчанию за «Готово» начислять баллы только за попадание, а не за правильность;
- не пытаться автоматически распознавать речь без отдельного явного требования.

### 12.6. Тип «Расставь по порядку»

- минимум 2 элемента;
- учитель задаёт правильный порядок;
- при старте элементы перемешиваются алгоритмом Fisher–Yates;
- ученик сортирует drag-and-drop, кнопками вверх/вниз и клавиатурой;
- кнопка «Проверить»;
- режим полного или частичного начисления баллов;
- не полагаться только на drag-and-drop, поскольку это нарушит клавиатурную доступность.

### 12.7. Валидация

Показывать ошибки рядом с конкретным полем. Перед экспортом выполнить общую проверку и вывести список проблем со ссылками на задания. Не блокировать скачивание из-за необязательных рекомендаций, но блокировать из-за отсутствия заданий, правильных ответов или повреждённых ассетов.

## 13. Окно задания и визуальные настройки

Окно задания появляется поверх сцены с затемнением фона, но HUD с текущим счётом может оставаться видимым.

Настройки:

- основной цвет карточки;
- цвет текста;
- цвет кнопок и активных вариантов;
- прозрачность карточки;
- скругление;
- толщина и цвет рамки;
- тень;
- свечение: включить/выключить, цвет, интенсивность, радиус;
- размер шрифта вопроса;
- размер шрифта ответов;
- начертание;
- выравнивание;
- ширина окна: компактная/средняя/широкая;
- анимация появления: без анимации, fade, scale, slide;
- скорость анимации.

Обязательная обратная связь:

- правильный ответ — карточка/рамка плавно загорается зелёным, появляется понятный текст и значок ✓;
- неправильный ответ — карточка/рамка плавно загорается красным, появляется текст и значок ошибки;
- цвет не должен быть единственным носителем смысла;
- оттенки успеха/ошибки должны сохранять контраст WCAG AA;
- после проверки выбор блокируется, чтобы результат нельзя было изменить задним числом;
- учитель выбирает: показать правильный ответ сразу или только после попытки/в конце.

## 14. Баллы, раунды и правила

Настраиваемая система:

- баллы за попадание по цели;
- баллы за правильный ответ;
- отдельные баллы за частично правильный ответ;
- штраф за промах (по умолчанию 0);
- штраф за неправильный ответ (по умолчанию 0, итоговый счёт не ниже 0);
- бонус за серию попаданий;
- бонус за скорость ответа;
- число раундов;
- число целей на раунд;
- число выстрелов;
- порог успешного прохождения в процентах;
- отображать или скрывать счёт до конца игры.

Пример безопасных значений по умолчанию:

- попадание: +10;
- верный ответ: +20;
- серия из 3: +5;
- промах и ошибка: 0;
- 1 раунд, 10 целей, 3 выстрела на цель/эпизод.

HUD показывает раунд, счёт, оставшиеся выстрелы и прогресс целей. Не привязывать HUD к английскому тексту и не допускать выхода длинных переводов за границы.

В финальном экране показать:

- итоговые баллы;
- число попаданий и промахов;
- точность;
- правильные/частичные/неправильные ответы;
- лучший серийный результат;
- нейтральную поддерживающую фразу;
- «Играть снова»;
- опциональную кнопку просмотра ошибок без раскрытия ответов, если учитель это запретил.

## 15. Звук и анимация

- отдельные переключатели музыки и эффектов;
- регулировка общей громкости;
- эффекты появления цели, выстрела, попадания, верного/неверного ответа, завершения;
- только авторские, лицензированные или синтезированные звуки;
- пользователь может загрузить собственные MP3/OGG/WAV с предупреждением о размере;
- браузерный autoplay не обходить: звук запускается после первого действия пользователя;
- уважать `prefers-reduced-motion`;
- режим «Минимум анимации» в настройках игры.

## 16. Формат проекта

Файл проекта скачивается, например, как `my-game.aimquiz.json` и содержит:

```json
{
  "schemaVersion": 1,
  "meta": {
    "title": "Название игры",
    "createdAt": "ISO_DATE",
    "updatedAt": "ISO_DATE",
    "appVersion": "SEMVER"
  },
  "locale": "ru",
  "translations": {},
  "scene": {},
  "targets": {},
  "helper": {},
  "tasks": [],
  "taskTheme": {},
  "rules": {},
  "audio": {},
  "assets": {}
}
```

Требования:

- версионирование схемы и миграции старых версий;
- строгая валидация при импорте;
- понятная ошибка без падения приложения;
- неизвестные/опасные поля не исполнять;
- пользовательские файлы хранить как безопасные data URL либо отдельную таблицу ассетов с ID;
- экспорт JSON создавать через Blob и `URL.createObjectURL`;
- после импорта предложить заменить текущий проект, если есть несохранённые изменения;
- автосохранение черновика и восстановление после перезагрузки;
- кнопка создания нового проекта с подтверждением.

## 17. Скачать HTML игры

Кнопка «Скачать HTML игры» обязана создавать один автономный `.html` файл:

- содержит весь HTML, CSS, JS, словари и ассеты;
- не обращается к localhost, npm, CDN или API;
- запускается по `file://` в актуальных Chrome, Edge, Firefox и Safari;
- адаптивно вписывается в окно, сохраняя 16:9;
- работает мышью, касанием и клавиатурой;
- содержит только игру, без панели редактора;
- имеет title, viewport, charset и базовые meta-теги;
- не использует `eval` и не выполняет пользовательский HTML;
- корректно экранирует `</script>`, кавычки и пользовательский текст при сериализации;
- показывает понятный экран запуска, чтобы пользовательским жестом разблокировать звук;
- включает кнопку полноэкранного режима, если API доступен;
- сохраняет лучший локальный результат только при включённой учителем настройке.

Перед сборкой HTML провалидировать проект. После сборки желательно выполнить smoke-test созданного runtime.

## 18. Код для Genially

Кнопка «Скопировать код для Genially»:

1. генерирует автономную версию игры;
2. формирует безопасный код вставки с адаптивным контейнером 16:9 и `iframe`;
3. копирует код через Clipboard API;
4. показывает уведомление «Код скопирован»;
5. при запрете Clipboard API показывает текстовое поле для ручного копирования.

Предпочтительный шаблон для опубликованного файла:

```html
<div style="position:relative;width:100%;padding-top:56.25%;overflow:hidden">
  <iframe
    src="PUBLIC_GAME_URL"
    title="Учебная игра"
    style="position:absolute;inset:0;width:100%;height:100%;border:0"
    allow="fullscreen; autoplay"
    loading="lazy">
  </iframe>
</div>
```

Важно: обычный iframe требует публичного HTTPS-адреса. Если в проекте нет публикации/хостинга, не обещай несуществующую ссылку. Предусмотри два честных режима:

- «Код по публичной ссылке» — учитель вставляет URL размещённого HTML;
- «Встроенный код» — `srcdoc` с тщательно экранированным содержимым, только если размер и ограничения Genially это допускают.

Если `srcdoc` слишком велик или платформа его фильтрует, показать инструкцию: сначала разместить скачанный HTML на доступном HTTPS-хостинге, затем вставить его URL. Не использовать `data:` URL как единственную стратегию. Выводить оценочный размер кода перед копированием.

## 19. Современный визуальный дизайн редактора

Стиль редактора:

- светлый современный интерфейс с опциональной тёмной темой;
- спокойный нейтральный фон, яркий акцентный цвет;
- карточки с умеренным скруглением и мягкой тенью;
- единая сетка отступов 4/8 px;
- ясная типографическая иерархия;
- кнопки с состояниями hover/focus/active/disabled/loading;
- иконки всегда сопровождаются tooltip или подписью;
- уведомления не перекрывают основные действия;
- skeleton/индикатор только для реально асинхронной загрузки;
- никаких декоративных миганий.

Использовать CSS design tokens: цвета, типографика, радиусы, тени, размеры панелей, длительности анимации. Проверить контраст и масштабирование браузера до 200%.

## 20. Нижний колонтитул

Внизу **самого редактора** постоянно разместить точный текст:

> Все права защищены и принадлежат Гальмиз Марии Александровне

Текст должен быть читаемым, не перекрывать панель и предпросмотр и корректно переноситься на узком экране. По умолчанию не добавлять его в экспортированную ученическую игру, если заказчик отдельно этого не потребует; можно предусмотреть настройку «Показывать авторскую строку в игре».

## 21. Доступность и безопасность

- семантические кнопки и поля с `label`;
- видимый `:focus-visible`;
- полная работа редактора форм и игры с клавиатуры;
- ARIA для диалогов, вкладок, уведомлений и сортируемых списков;
- focus trap в модальном задании и возврат фокуса после закрытия;
- alt-текст для учебных изображений;
- не сообщать результат только цветом или звуком;
- уважать системные настройки уменьшения движения;
- минимальный размер touch-target 44×44 px;
- санитизация пользовательских имён файлов и текстов;
- никакого выполнения импортированного кода;
- защита от XSS при создании HTML и `srcdoc`;
- URL пользовательских Blob освобождать после замены/размонтирования;
- приложение по умолчанию не собирает данные учеников и не отправляет аналитику.

## 22. Производительность

- стабильная анимация, целевой показатель 60 FPS на обычном учебном ноутбуке;
- перемещать цели через `transform`, а не `top/left`;
- использовать `requestAnimationFrame` для игрового цикла;
- паузить цикл в скрытой вкладке;
- не рендерить заново всю левую панель при движении прицела;
- разделить состояние редактора и высокочастотное runtime-состояние;
- оптимизировать/предупреждать о слишком больших изображениях;
- не допускать утечек таймеров, listeners, Blob URLs и Audio nodes;
- проект с 100 заданиями должен оставаться редактируемым без заметных задержек.

## 23. Рекомендуемая архитектура

Разделить домены:

```text
src/
  editor/         # панели, формы, библиотека ассетов
  game/           # независимый игровой runtime и конечный автомат
  preview/        # мост между конфигурацией редактора и runtime
  tasks/          # модели и UI четырёх типов заданий
  i18n/           # системные словари
  assets/         # встроенные авторские ассеты и манифест
  persistence/    # autosave, import/export, migrations
  exporters/      # standalone HTML и Genially embed
  shared/         # типы, UI primitives, utils
```

Ключевые правила:

- единая типизированная `ProjectConfig` является источником правды;
- игровая логика не зависит от компонентов редактора;
- экспорт использует тот же runtime, что и предпросмотр, чтобы поведение не расходилось;
- случайность инкапсулировать и разрешить seed для воспроизводимых тестов;
- начисление баллов оформить чистыми функциями;
- таймеры и переходы состояния централизовать;
- встроенные ассеты описывать манифестом, а не массивами внутри UI.

## 24. Undo/Redo и история

- история минимум на 50 осмысленных действий;
- набор текста объединять в одно действие по debounce, а не создавать запись на каждый символ;
- загрузку ассета, удаление задания и сортировку можно отменить;
- не записывать в историю движение прицела и игровое тестирование;
- после Undo/Redo предпросмотр обновляется без перезагрузки;
- после импорта история начинается с нового безопасного состояния.

## 25. Пустые, загрузочные и ошибочные состояния

Обязательно реализовать:

- стартовый проект с 3–4 демонстрационными заданиями всех типов;
- понятный экран, если заданий нет;
- миниатюру-заглушку при ошибке ассета;
- уведомление о неподдерживаемом файле;
- обработку превышения размера;
- восстановление после повреждённого автосохранения;
- диалог ошибок экспорта без потери проекта;
- fallback системного шрифта и отсутствующего звука.

## 26. Тесты и критерии приёмки

### 26.1. Unit/интеграционные тесты

Проверить:

- расчёт баллов и бонусов;
- все переходы конечного автомата;
- выбор вопросов без повторов;
- проверку одного и нескольких ответов;
- частичную оценку;
- проверку правильного порядка;
- Fisher–Yates с фиксированным seed;
- локализацию и fallback;
- сериализацию/десериализацию проекта;
- миграцию версии схемы;
- экранирование пользовательского текста в HTML;
- генерацию embed-кода;
- undo/redo.

### 26.2. E2E-сценарии

1. Учитель создаёт проект, меняет язык — все системные плашки предпросмотра меняются, вопросы остаются прежними.
2. Учитель выбирает фон, цель и помощника — каждый сразу появляется без белой вспышки.
3. Учитель загружает собственные изображения — они видны в предпросмотре и после повторной загрузки проекта.
4. Учитель создаёт по заданию каждого из четырёх типов и тестирует их.
5. Попадание открывает ровно одно задание; правильный ответ даёт зелёную обратную связь и баллы, неправильный — красную.
6. Сортировка по порядку работает мышью и клавиатурой.
7. Проект скачивается и загружается без потери настроек и ассетов.
8. Автономный HTML открывается офлайн и полностью проходит игру.
9. Код Genially копируется либо предлагается ручное копирование.
10. При 30 быстрых изменениях текста предпросмотр не мигает и не сбрасывается.
11. Пауза действительно останавливает цели и таймеры, продолжение не создаёт дубликаты.
12. Игра работает при touch-вводе и при управлении клавиатурой.

### 26.3. Definition of Done

Работа считается завершённой, только если:

- нет декоративных заглушек вместо функций;
- нет неработающих кнопок;
- реализованы все четыре типа заданий;
- присутствуют встроенные фоны, цели и помощники, а также загрузка пользовательских;
- локализация меняет все системные элементы;
- предпросмотр стабилен и тестируем;
- JSON-импорт/экспорт проходит round-trip;
- автономный HTML работает без интернета;
- предусмотрен честный сценарий вставки в Genially;
- ключевые тесты проходят;
- в редакторе присутствует точная строка об авторских правах;
- README содержит команды запуска, сборки, тестов и описание форматов.

## 27. Порядок реализации

1. Проанализировать существующий репозиторий и референсы, сохранить совместимость со стеком.
2. Описать типы `ProjectConfig`, `Task`, `Asset`, словари и схему миграций.
3. Создать стабильный layout редактора и дизайн-токены.
4. Реализовать независимый игровой runtime и конечный автомат.
5. Реализовать библиотеку/загрузку ассетов.
6. Реализовать четыре редактора заданий и игровое окно ответа.
7. Соединить формы с предпросмотром без перезагрузки runtime.
8. Добавить локализацию, правила баллов, звук и доступность.
9. Реализовать автосохранение, JSON import/export и undo/redo.
10. Реализовать автономный HTML exporter и Genially embed.
11. Добавить тесты, проверить офлайн-работу и устранить ошибки.
12. Провести финальный аудит по Definition of Done.

## 28. Правила работы ИИ-разработчика

- Сначала изучи файлы проекта; не удаляй и не перезаписывай пользовательские изменения.
- Не спрашивай о мелочах, которые можно решить безопасным профессиональным значением по умолчанию.
- Если отсутствуют графические ассеты, создай оригинальные временные векторные/процедурные ассеты в едином стиле и явно опиши, как их заменить. Не копируй защищённые материалы.
- После каждого крупного этапа запускай релевантные тесты и исправляй найденные проблемы.
- Не заявляй о завершении без фактической проверки сборки и основных сценариев.
- Любой компромисс, влияющий на автономность экспорта, доступность, безопасность или Genially, зафиксируй в README.
- При конфликте требований приоритет: сохранность данных → безопасность → работа экспорта → игровая логика → доступность → визуальные эффекты.

## 29. Финальный отчёт ИИ

После реализации кратко сообщи:

- что создано;
- где находятся основные файлы;
- какие команды запускают приложение и тесты;
- какие проверки выполнены и с каким результатом;
- как скачать/загрузить проект;
- как получить автономный HTML;
- как вставить игру в Genially и какие ограничения у выбранного способа;
- какие ассеты являются встроенными и как добавить свои.
